# /support: Discord-login ticket system

`/support` is the Xotiic Support ticket system, built into the main site. It uses the site's navbar, footer and theme. It runs entirely inside the **Next.js frontend** (`xotiictech-web`) and never touches FastAPI.

| URL | Who | What |
|---|---|---|
| `/support` | everyone | overview, ticket bot status, stats |
| `/support/tickets` · `/support/tickets/new` · `/support/tickets/:id` | anyone logged in with Discord | your tickets, open a ticket, read and reply |
| `/support/exotic/*` | Discord users holding `STAFF_ROLE_ID` | dashboard, queue, ticket detail (claim/assign/close/reopen/priority/reply/notes), staff stats, audit log |

Anyone who isn't staff and opens `/support/exotic` is sent to `/support`, and the staff API answers `404`, so the panel doesn't reveal that it exists. The panel is separate from the `/xotiic` admin panel.

## How it fits

```
browser ─► /support/*            Next.js pages (server components)
        ─► /support/api/*        Next.js route handlers  ──► Supabase Postgres, schema "support" (Prisma)
                                                          ──► Discord REST (bot token: role checks, history)
                                                          ──► Ticket X internal API (create/reply/close)
Ticket X bot ─► /support/api/bots/heartbeat   (every 30s, drives the online dot)
             ─► /support/api/bot/events       (ticket + message sync)
/api/*  is still proxied to FastAPI, unchanged.
```

- **Database:** its own Postgres schema, `support`, set by `?schema=support` in the URLs. It can share the Supabase project the API already uses without touching the API's tables.
- **Login:** Auth.js with Discord (`identify guilds`), under `/support/api/auth`. Sessions are signed httpOnly cookies. Staff status is checked against Discord on every request (60-second cache), never stored in the cookie.
- **Security:** zod validation, same-origin plus JSON-only CSRF checks, rate limits (3 tickets/hour, 10 replies/minute, 60 staff actions/minute), and an audit log of every staff action.

## Setup

### 1. Supabase

Use the same Supabase project as the API, or a separate one. Supabase → **Connect** → **ORMs** → **Prisma** shows two strings. Add the `support` schema to both:

| Render key (on **xotiictech-web**) | Value |
|---|---|
| `SUPPORT_DATABASE_URL` | transaction pooler, port **6543**: `...pooler.supabase.com:6543/postgres?pgbouncer=true&schema=support` |
| `SUPPORT_DIRECT_URL` | session pooler, port **5432**: `...pooler.supabase.com:5432/postgres?schema=support` |

Use the `pooler.supabase.com` hosts. The username is `postgres.<project-ref>`. If the password has symbols, URL-encode them or reset it to letters and numbers.

The tables are created automatically on deploy by `npm run support:setup`. If those two variables are missing, the step is skipped, the rest of the site still deploys, and `/support` shows "being set up".

### 2. Discord application

Developer Portal → your app → **OAuth2**:

- **Redirects:** add `https://<your-site>/support/api/auth/callback/discord`. Add the `www.` version too if you use it. Then click **Save Changes**.
- Copy the **Client ID** and **Client Secret**.

### 3. Render environment (xotiictech-web)

| Key | Value |
|---|---|
| `SUPPORT_DATABASE_URL`, `SUPPORT_DIRECT_URL` | from step 1 |
| `AUTH_SECRET` | auto-generated by the blueprint (or any 32+ char random string) |
| `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET` | from step 2 |
| `DISCORD_BOT_TOKEN` | Ticket X's bot token (server-side only) |
| `DISCORD_GUILD_ID` | your support server ID |
| `STAFF_ROLE_ID` | staff role ID; comma-separate several |
| `BOT_HEARTBEAT_SECRET` | the same value as `BOT_HEARTBEAT_SECRET` in the bot's `.env` |
| `BOT_API_URL`, `BOT_API_SECRET` | the bot's internal API (section B). Leave empty until it exists |

The **Join Discord** button on `/support` uses the `discord` link from **/xotiic → Site content → socials**.

### 4. Ticket X bot `.env`

```
WEBSITE_HEARTBEAT_URL=https://<your-site>/support/api/bots/heartbeat
BOT_HEARTBEAT_SECRET=<same value as on Render>
```

Re-upload the bot to Discloud, since Discloud only reads the `.env` inside the zip. The online dot on `/support` turns green within about 30 seconds.

## Bot contract

All bot → site requests send `Authorization: Bearer <BOT_HEARTBEAT_SECRET>`. Responses are `{ "data": ... }` or `{ "error": { "code", "message" } }`.

### A1. `POST /support/api/bots/heartbeat`

Body: `{ "botKey": "ticket-bot" }`. Already implemented in the bot (`src/services/websiteHeartbeat.js`).

### A2. `POST /support/api/bot/events` (to build on the bot side)

One event per request. Every event is idempotent.

```json
{ "type": "ticket.upsert", "ticket": { "guildId": "…", "number": 42, "channelId": "…", "openerId": "…", "openerName": "someone",
  "category": "support", "subject": "…", "state": "open", "priority": "normal", "claimedById": null,
  "createdAt": "2026-10-23T10:00:00.000Z", "closedAt": null, "firstResponseAt": null, "lastActivityAt": "…" } }

{ "type": "message.create", "message": { "guildId": "…", "ticketNumber": 42, "discordMessageId": "…", "authorId": "…",
  "authorName": "someone", "isStaff": false, "content": "…", "createdAt": "…" } }

{ "type": "audit", "entry": { "actorId": "…", "actorName": "staff", "action": "ticket.claim", "ticketNumber": 42, "guildId": "…" } }
```

- **Partial updates:** send only the fields that changed. Missing fields are left alone.
- **Order:** send `ticket.upsert` before a ticket's messages. Otherwise you get `404 ticket_not_found`.
- **Timestamps:** convert the bot's millisecond times to ISO strings.
- **Field mapping:** `user_id` → `openerId`, `claimed_by` → `claimedById`.

### B. Site → bot internal API (to build on the bot side)

The bot exposes an HTTP API and checks `Authorization: Bearer <BOT_API_SECRET>`. Until it exists, opening, replying and staff actions show "isn't connected to the bot yet" and change nothing.

| Endpoint | Body | Returns |
|---|---|---|
| `POST /internal/tickets` | `{ openerId, openerName, category, subject, description }` | `{ guildId, number, channelId, channelUrl, state, createdAt }` |
| `POST /internal/tickets/:number/messages` | `{ guildId, ticketNumber, authorId, authorName, content, isStaff }` | `{ discordMessageId, createdAt }` |
| `POST /internal/tickets/:number/actions` | `{ action, guildId, ticketNumber, actorId, actorName, assigneeId?, reason?, priority? }` with action `claim/unclaim/assign/close/reopen/priority` | `{ ok: true }` |

Return `4xx` with `error.message` for rule violations (cooldown, blacklist, already closed); it's shown to the user. Return `5xx`, or time out, when the bot is unavailable.

> Discloud apps of type `bot` usually can't receive incoming HTTP. If that's the case for yours, section B needs a pull-based queue instead: the site stores jobs and the bot polls for them. Ask before building it.
